NVNM Chain verifies passkey (WebAuthn/P256) signatures in the protocol itself. You can turn a passkey into an account without a smart-contract wallet, bundler or seed phrase.

This guide explains how NVNM Chain supports passkeys. It then walks through the passkey wallet in the NVNM demo dApp. You learn how to create an account, store its public key, restore it in a new browser and sign transactions.

## How passkeys work on the chain

Standard Ethereum accounts accept only secp256k1 signatures and use sequential nonces. That rules out modern sign-in methods such as passkeys, and sequential nonces cap how many transactions an app can push through at once.

NVNM Chain addresses this with its native transaction type (`0x76`), an [EIP-2718](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-2718.md) typed transaction. Besides secp256k1, a `0x76` transaction can carry a P256 or WebAuthn signature, and the protocol validates it directly. A passkey can therefore sign transactions without a verifier contract or a smart-contract wallet.

The demo dApp describes its passkey account the same way: "a chain-native WebAuthn P-256 account" (`apps/web/README.md`).

### Signature types

A signature's first byte (or, for secp256k1, its 65-byte length) tells the chain which of four schemes it uses.

Each scheme has its own base transaction cost, which reflects how much computation its verification takes. The last column below shows that base transaction cost, not the cost of the signature check alone. The secp256k1 base of 21,000 gas already includes 3,000 gas for the `ecrecover` precompile. P256 adds another 5,000 gas for P256 verification.

| Type      | Wire format                                                                                                                                   | How the chain verifies it                                                                                            | Base transaction gas                       |
|-----------|-----------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------|--------------------------------------------|
| secp256k1 | 65 bytes, no type prefix (backward compatible)                                                                                                | Standard `ecrecover`                                                                                                 | 21,000                                     |
| P256      | Prefix `0x01` + 129 bytes (`r`, `s`, `pub_key_x`, `pub_key_y`, `pre_hash`). 130 bytes total.                                                  | P256 curve verification with the provided public key. If `pre_hash` is `true`, the digest is `sha256(digest)` first. | 26,000                                     |
| WebAuthn  | Prefix `0x02` + `webauthn_data` (`authenticatorData` ‖ `clientDataJSON`) + 128 bytes (`r`, `s`, `pub_key_x`, `pub_key_y`). 129 to 2049 bytes. | Parse `clientDataJSON`, verify challenge and type, then P256 verify                                                  | 26,000 + calldata gas for `clientDataJSON` |
| Keychain  | Prefix `0x03` + `user_address` (20 bytes) + inner signature                                                                                   | Verify the inner signature, then validate the access key in the AccountKeychain precompile                           | Inner signature + 3,000                    |

A passkey produces a WebAuthn signature with this layout:

```rust title="WebAuthn signature"
pub struct WebAuthnSignature {
    typeId: u8,                 // 0x02
    webauthn_data: Bytes,       // Variable length (authenticatorData || clientDataJSON)
    r: B256,                    // 32 bytes
    s: B256,                    // 32 bytes
    pub_key_x: B256,            // 32 bytes
    pub_key_y: B256             // 32 bytes
}
```

Keep the WebAuthn payload small. If your wallet sends the minimum 37-byte `authenticatorData`, without the AT or ED flags, the transaction costs less gas and the chain has less to parse.

### How a passkey becomes an address

For P256 and WebAuthn keys, the chain derives the address from the public key alone:

```solidity title="P256 and WebAuthn address derivation"
function deriveAddressFromP256(bytes32 pubKeyX, bytes32 pubKeyY) public pure returns (address) {
    // Hash
    bytes32 hash = keccak256(abi.encodePacked(
        pubKeyX,
        pubKeyY
    ));

    // Take last 20 bytes as address
    return address(uint160(uint256(hash)));
}
```

Two consequences follow for your app:

- **You must keep the public key.** The address is derived from the public key, but the device holds only the passkey's credential ID. The authenticator never hands the key back after registration. Record it when the passkey is created, for example on your server or in browser storage. When the user returns, supply it through `getPublicKey` in viem's passkey sign-in flow (see [viem: Sign in with a passkey](https://viem.sh/tempo/guides/accounts/passkeys)).
- **One passkey is one account.** The formula takes no chain ID. The demo dApp tells its users: "Your address comes from the passkey, so creating another makes a new, empty account... It's the same address on testnet and devnet, with a separate balance on each."

### What the chain checks, and what it skips

The chain's WebAuthn verification follows the [Daimo P256 verifier approach](https://github.com/daimo-eth/p256-verifier/blob/master/src/WebAuthn.sol). The challenge is the transaction hash, Base64URL-encoded. The signed message is `sha256(authenticatorData || sha256(clientDataJSON))`.

| The chain verifies                                     | The chain skips                                                                   |
|--------------------------------------------------------|-----------------------------------------------------------------------------------|
| `authenticatorData` length: 37 bytes or more           | Origin: a transaction isn't tied to a web page                                    |
| User Presence (UP) flag: must be set                   | RP ID hash: there's no relying party to compare it against                        |
| `clientDataJSON` type: `"type":"webauthn.get"`         | Signature counter: clone detection is up to your app                              |
| Challenge: the transaction's `tx_hash`, in Base64URL   | Backup flags: whether to require backed-up passkeys is an account-level choice    |
| P256 signature: must be valid                          |                                                                                   |

Because the chain skips origin and RP ID checks, the chain does not bind a passkey to your domain. The browser does. Keep this in mind when you read the [security notes](#security-and-operational-notes).

### Passkey prompts and access keys

If the passkey is the account's only key, every transaction triggers a biometric or PIN prompt. Apps that send many transactions in a row feel slow. The prompt may also be labeled "Sign in", which looks odd when the user is approving a transaction.

An access key fixes this. The passkey authorizes a separate, limited signing key once, and that key signs follow-up transactions without a prompt. The AccountKeychain precompile at `0xAAAAAAAA00000000000000000000000000000000` manages access keys.

Contract creation is reserved for the root key. An access key can't sign a transaction that runs `CREATE` or `CREATE2`, whether directly or through a factory contract.

<Note>
  The demo dApp keeps access keys off. Every transaction asks for the passkey, and its UI warns users that "your device's prompt may say 'Sign in'". To add access keys, see viem's [access keys guide](https://viem.sh/tempo/guides/access-keys).
</Note>

## The SDKs to use

The demo dApp builds its passkey wallet on three TypeScript packages that support NVNM Chain's `0x76` transactions:

| Package                 | Role                                                                                                       | Version in the demo dApp           |
|-------------------------|------------------------------------------------------------------------------------------------------------|------------------------------------|
| `wagmi` (`wagmi/tempo`) | The [`webAuthn` connector](https://wagmi.sh/tempo/connectors/webAuthn), which connects a WebAuthn EOA      | `wagmi` 3.7.7, `@wagmi/core` 3.6.5 |
| `accounts`              | The Accounts SDK (the `accounts` package). The wagmi `webAuthn` connector is a thin wrapper around it.     | 0.18.4                             |
| `viem` (`viem/tempo`)   | The chain config, `Account.fromWebAuthnP256` and the serializers for `0x76` transactions                   | `^2.57.1` (2.57.1 resolved)        |

The demo dApp's passkey ceremony also uses `ox` 0.14.45 and `webauthx` 0.1.2, the versions `accounts` 0.18.4 resolves. Its `pnpm-workspace.yaml` pins `wagmi`, `@wagmi/core`, `accounts`, `ox` and `webauthx` to exact versions (viem is `^2.57.1`), so re-test before you bump them.

A minimal setup registers the connector in a wagmi config. This example uses the `nvnmTestnet` chain that the first step below defines in `chains.ts`:

```ts title="wagmi.config.ts"
import { createConfig, http } from 'wagmi'
import { webAuthn } from 'wagmi/tempo'

import { nvnmTestnet } from './chains'

export const config = createConfig({
  connectors: [webAuthn()],
  chains: [nvnmTestnet],
  multiInjectedProviderDiscovery: false,
  transports: {
    [nvnmTestnet.id]: http(),
  },
})
```

By default, the connector runs the passkey ceremony locally in the browser. To fetch registration and authentication challenges from a server endpoint instead, set `authUrl`: `webAuthn({ authUrl: '/api/webauthn' })`. To plug in your own ceremony, pass `ceremony`. The demo dApp does this.

<Info>
  This guide uses domain-bound passkeys, as the demo dApp does. Your app creates and uses the passkeys under its own domain, so you control the wallet UI and the WebAuthn flow end to end.
</Info>

## Where the dApp stores passkey data

The dApp stores passkey data in IndexedDB, not `localStorage`. `Storage.idb` is the Accounts SDK's IndexedDB adapter. In the browser, `Provider.create` uses this adapter unless you pass another one.

The adapter writes to an IndexedDB database named `tempo`. It prefixes every key with `options.key`. Give each app on a shared origin its own prefix. Otherwise one app can overwrite another's stored keys.

With `key: "nvnm-demo-dapp"`, the dApp's data lives under these keys:

| IndexedDB key | Written by | Contents |
| --- | --- | --- |
| `nvnm-demo-dapp.credentials` | The ceremony, on registration and recovery | A map from credential ID to the passkey's uncompressed P-256 public key (hex) |
| `nvnm-demo-dapp.lastCredentialId` | The SDK's WebAuthn adapter, after create and sign-in | The ID of the last passkey used |

The SDK also persists its provider state, such as the connected accounts, through the same storage adapter.

<Warning>
  The app never stores a private key. The authenticator holds it. The dApp stores only public keys and account metadata. Its UI says: "This site never sees its private key."
</Warning>

The key names come from the internals of `accounts` 0.18.4, which the dApp relies on. The SDK doesn't document them, so check them again when you upgrade it.

## Restore an account in a new browser

WebAuthn returns a passkey's public key only when the passkey is created. If a user signs in from another device with a synced passkey, or after clearing site data, the browser has no stored key. The SDK's local ceremony then fails with `Unknown credential`.

The recommended fix is to save the public key on your side at registration time. The Accounts SDK provides a server-backed ceremony for this. The demo dApp has no backend, so it uses its own technique instead. ECDSA public-key recovery yields two candidate public keys per signature. The dApp asks for a second signature from the same passkey, keeps the one key that both sets share, and stores it:

```ts title="apps/web/src/lib/passkey-ceremony.ts"
import { type Storage, WebAuthnCeremony } from "accounts";
import { Bytes, Hash, P256, PublicKey, Signature } from "ox";
import type { Hex } from "viem";
import { Authentication } from "webauthx/client";

// ...

// Where accounts 0.18.4's `WebAuthnCeremony.local` keeps its credential id → public key map (uncompressed P-256,
// hex). Recovered keys go into the same map, so the next sign-in on this device takes the local path.
const credentialsKey = "credentials";

// ...

// The accounts SDK's local ceremony, able to sign in with a passkey this browser has never seen.
//
// WebAuthn only returns a passkey's public key when it is created, and the local ceremony keeps it in this browser's
// storage, so a passkey synced to another device, or used after site data is cleared, fails with "Unknown credential".
// There is no backend to ask. Instead, ECDSA public-key recovery gives two candidate keys per signature; a second
// signature by the same passkey, over a fresh challenge, shares exactly one of them: the passkey's key.
export function recoveringCeremony({
  storage,
  rpId,
  sign = Authentication.sign,
}: RecoveringCeremonyOptions): Ceremony {
  const local = WebAuthnCeremony.local({ storage, rpId });
  // Candidates from a recovery whose second prompt failed, by credential id, so a retry needs a single prompt.
  const pending = new Map<string, readonly Hex[]>();

  async function storedKeys() {
    return (await storage.getItem<Record<string, Hex>>(credentialsKey)) ?? {};
  }

  async function remember(credentialId: string, publicKey: Hex) {
    await storage.setItem(credentialsKey, { ...(await storedKeys()), [credentialId]: publicKey });
    pending.delete(credentialId);
    return { credentialId, publicKey };
  }

  return WebAuthnCeremony.from({
    ...local,
    async verifyAuthentication(response) {
      // The local ceremony's `verifyAuthentication` is this lookup, but throws where an unknown key starts recovery. A
      // stored key must also have made this signature: any page on this origin can write the map, and a wrong entry
      // would otherwise give the wrong address on every sign-in. Recovery replaces it.
      const known = (await storedKeys())[response.id];
      if (known && signedBy(response, known))
        return { credentialId: response.id, publicKey: known };

      const candidates = recoverCandidates(response);
      const earlier = pending.get(response.id);
      const recovered = earlier && commonKey(earlier, candidates);
      if (recovered) return remember(response.id, recovered);

      // If this prompt is cancelled the error propagates and `pending` keeps these candidates.
      pending.set(response.id, candidates);
      const { options } = await local.getAuthenticationOptions({ credentialId: response.id });
      const second = await sign({ options });
      // From here a failure can't tell which signature was wrong, so a retry starts over.
      pending.delete(response.id);
      if (second.id !== response.id) {
        throw new PasskeyRecoveryError(
          `Expected a second signature from passkey ${response.id}, got one from ${second.id}.`,
        );
      }
      const publicKey = commonKey(candidates, recoverCandidates(second));
      if (!publicKey) {
        throw new PasskeyRecoveryError(
          `The two signatures from passkey ${response.id} don't share a public key.`,
        );
      }
      return remember(response.id, publicKey);
    },
  });
}

// What a WebAuthn authenticator signs: sha256(authenticatorData ‖ sha256(clientDataJSON)).
function signedPayload(response: AuthenticationResponse) {
  const { authenticatorData, clientDataJSON } = response.metadata;
  return Hash.sha256(
    Bytes.concat(Bytes.fromHex(authenticatorData), Hash.sha256(Bytes.fromString(clientDataJSON))),
  );
}

// ...

// The public keys that could have produced this assertion's signature, one per y-parity of the curve point R, in the
// format the SDK stores. Parities that don't yield a point are skipped.
function recoverCandidates(response: AuthenticationResponse): Hex[] {
  const payload = signedPayload(response);
  const { r, s } = Signature.fromHex(response.signature);
  const candidates: Hex[] = [];
  for (const yParity of [0, 1]) {
    try {
      candidates.push(
        PublicKey.toHex(P256.recoverPublicKey({ payload, signature: { r, s, yParity } })),
      );
    } catch {
      // No curve point for this parity.
    }
  }
  return candidates;
}

// The one key both candidate sets share. Two shared keys mean the second signature repeats the first (the same r and
// s, up to the sign of s, over the same payload), which doesn't single out a key, so that counts as no match.
function commonKey(a: readonly Hex[], b: readonly Hex[]): Hex | undefined {
  const common = a.filter((key) => b.includes(key));
  return common.length === 1 ? common[0] : undefined;
}
```

View on GitHub: [`apps/web/src/lib/passkey-ceremony.ts`](https://github.com/NVNM-Chain/nvnm-demo-dapp/blob/main/apps/web/src/lib/passkey-ceremony.ts)

Here is what this means for your users:

- In a browser that already stores the key, sign-in takes one prompt. The ceremony still checks that the stored key made the signature, because "any page on this origin can write the map".
- In a new browser, sign-in takes two prompts. The dApp tells users: "In a browser you haven't used this passkey in, you'll confirm twice so we can recover your account."
- After recovery, the key is stored, so the next sign-in takes one prompt.

`signedPayload` computes the same message that the chain's WebAuthn verifier checks: `sha256(authenticatorData || clientDataHash)`.

<Note>
  Two-signature recovery is the demo dApp's own approach, not a feature of the chain or the SDK.
</Note>

### Use a server-backed ceremony in production

`WebAuthnCeremony.local` generates and checks challenges in the browser, with no server involved. That's convenient while you build, but a production app should issue challenges from its own server. The SDK's server-backed ceremony does this. Mount `Handler.webAuthn` from `accounts/server`. Then point the connector at it with `webAuthn({ authUrl: '/auth' })`:

```ts title="Server"
import { Handler, Kv } from 'accounts/server'

export const handler = Handler.webAuthn({
  kv: Kv.memory(),
  origin: 'https://app.example.com',
  rpId: 'example.com',
})
```

The example keeps challenges in memory with `Kv.memory()`, which loses them on restart and isn't shared across instances. Swap in a persistent `Kv` adapter before you deploy.

## Security and operational notes

### Passkeys are bound to the domain

The browser binds every passkey to an RP ID. In the demo dApp, the RP ID is the page's hostname. Its README explains the consequences:

> **Passkeys are bound to the domain.** A passkey belongs to the hostname it was created on, so production passkeys belong to `nvnm-chain.github.io`, and `localhost` (dev and `vp preview`) has its own. Every NVNM-Chain GitHub Pages site shares that hostname and its storage: any of them can ask for these passkeys and, with the user's biometric, sign for their accounts, so only trusted repos should publish to the org's Pages. A custom domain avoids that, but moving the app to another domain orphans every existing passkey account: the passkey can't be used there, so the app can no longer sign for that address. Settle the domain before promoting passkeys.
>
> — Demo dApp `README.md`

Decide on `rpId` early. A passkey registered for a parent domain (`example.com`) can be used on its subdomains, such as `app.example.com`, as WebAuthn's RP rules permit. A passkey registered for a subdomain (`app.example.com`) can't move up to the parent domain (`example.com`).

Changing `rpId` after launch is effectively a breaking change. Passkeys registered under the old value may no longer be usable, and affected users would have to create new ones.

The browser enforces this binding. NVNM Chain doesn't.

### Serve passkeys from a secure origin

- Browsers expose WebAuthn only in a [secure context](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts): HTTPS pages, plus `localhost` for development. Deploy over HTTPS, or passkey creation and sign-in won't start at all.
- In development, open your app at `localhost`. The dApp's README warns: "an IP address such as `127.0.0.1` isn't a valid passkey domain, so passkeys fail there."
- `localhost` and your production host hold different passkeys, so they are different accounts.

### Plan for lost passkeys

There is no seed phrase. The dApp warns its users: "If every copy of the passkey is lost or deleted, the account and its funds are gone. Passkeys synced by iCloud Keychain or Google Password Manager also work on your other devices signed in to the same Apple or Google account."

Not every user has passkey sync turned on, and some use different password managers on different devices. Losing all of a user's devices at once is possible too. Let users register more than one passkey from the start, so one lost device doesn't lock them out.

### Fund new accounts

A new passkey account is empty. The dApp tells users: "New passkey accounts start with 0 nUSD, and network fees are paid in nUSD." Point your users to a faucet:

- Testnet: [nUSD faucet](/getting-started/nusd-faucet-testnet)
- Devnet: [nUSD faucet](/developer-guides/pathusd-faucet-devnet)

The dApp uses nUSD, the TIP-20 at `0x20C0000000000000000000000000000000000000`, as the fee token on both networks. To learn how fees work, see [Token balances and fees](/developer-guides/token-balances-and-fees#how-fees-work). Check [Network details](/resources/network-details) for each faucet's current status.
